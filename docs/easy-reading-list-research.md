# 文章列表好讀模式：困難點本質與未來方向

撰於 2026-07-05（v4 之後）、2026-07-25 精簡。用途：**決定該功能方向前先讀**——為何這功能結構性地難、為何不再追 native parity、若要重啟該往哪走。現行架構與不變量在 `docs/easy-reading-list.md`。

決策現況：使用者拍板走 **v5「封閉互動＋確定性交易」**（介於下述 C 與 D：保留終端外觀與鍵盤習慣，互動合約封閉化、交易尾附 Ctrl+L）。

## 1. 困難點本質

原生模式的 client 是**顯示玻璃**：`term_buf` 只解 ANSI、畫格子，不理解內容。游標、翻頁、選取、置底、搜尋的語意全在 server ⇒ **任何 server 行為自動正確**。好讀列表要在使用者與 server 之間插一層自己的列表狀態（緩衝多頁、隱藏部分列、本地游標），從此 client 必須**理解**畫面（分類指紋）、**預測** server（read.c 語意）、**對帳**（settle／expect）。單一真相源變雙真相源，任何同步誤差＝一個 bug。

六個結構性因素（**都不會因為繼續修而縮小**）：

1. **協定無規格**。唯一介面是 80×24 字元流；何時「回應結束」、哪幾列會髒、游標停哪，pttbbs 沒有合約，只能逆向原始碼＋錄影帶實錄（`docs/pttbbs-screen-protocol.md`）。每條沒逆向到的行為＝上線後一輪修復。
2. **settle 判定**。server 寫入是增量、可黏包（OBUFSIZE 3072 拆包＋WS proxy 邊界 unknown），「畫面到齊」只能靠 50ms 靜默窗推定；本地導覽約 30ms 一幀重繪與之交錯，gating 沒切乾淨就 settle 餓死（不變量 2b）。
3. **typeahead 跳繪**。pttbbs 在輸入 buffer 非空時直接跳過重繪（PTT 編的是 `mbbsd/pfterm.c#refresh`，非 screen.c；兩者同義）⇒ 機器送鍵必須全序列化（CommandQueue 單 in-flight）。這是 v3 的 source 級死因。
4. **隱藏列改變幾何**。隱藏 N 列後 24 行視窗要用其他頁的列補滿 → 必須超前抓頁＋自己算視窗，還要在 server 真游標與本地假游標間往返對位（`●` 污染列 bug 一族全源於此）。
5. **狀態爆炸**。原生單態 vs「5 狀態 × 3 渲染模式 × 佇列 in-flight × 預讀鏈態」，每個交互組合都是可能漏掉的格子。
6. **驗收標準無界**。若承諾「與原生無可感知差異」，QA 面就是 **PTT 的全部互動面**（`/` 搜尋、`Z`、精華區、水球、動態看板、推文數即時變化、刪文位移、置底文…）——native 對這一切免費正確，仿真層每項都要分類、要嘛支援要嘛降級。

**最重要的一條經驗定律：「測試全綠 ≠ 實測穩」已跨 v3/v4 兩代重現**——失敗面積在測試素材之外。故 v5 合約明確**不承諾** parity（見 `easy-reading-list.md` 核心原則）。

## 2. 方案光譜（決策座標，供未來重啟時定位）

| 方案 | 做法 | 協定介入 | 失敗模式 | 成本 |
|---|---|---|---|---|
| A 原生就地遮蔽（**一直在服役**） | 黑名單列在原生模式渲染成被刪除樣式通知列 | 零 | 無 | 已完成 |
| C 原生視窗仿真（v4／現行 v5 基礎） | 雙真相源＋24 行視窗 | 重 | 見第 1 節 | 已投入，續修無界 |
| D App 式視圖 | 資料層＋虛擬列表，無終端概念 | 中（無狀態交易） | 載入等待顯性化（骨架列） | 週級 |

初衷「不想看到黑名單的文」在 A 就已達成；C／D 解的是更高目標——「像那些文不存在一樣連續閱讀」。

## 3. BePTT 的穩定性來自哪（外部參考，不可由本專案 code 反推）

素材：`3rd_script/BePTT/`（v7.0.9 xapk 解包＋jadx 反編譯；**gitignored**）。

| 面向 | 實作 | pointer |
|---|---|---|
| 終端模型 | 72×80 `char[][]`＋色彩陣列，ANSI 單一 regex `\e\[([0-9;]*)([ABCDHJKmsu])` | `Z7/f.java:489,495` |
| 互動 | **寫死字串腳本**，每步「連按離開鍵盲退歸位 → 重新導航」（如 `"eeeqqqs"＋板名＋"\r\n$$…\f"`） | `N7/P.java:301,305,580` |
| 到齊判定 | 指令尾附 `\f`（Ctrl+L 強制全幅重繪）→ 輪詢畫面特徵字串（row0 標題＋row23 footer），5s timeout | `N7/P.java:307-314` |
| 失敗處理 | timeout 重試 4 次 → 錯誤對話框 | ConnectPttActivity:1007-1027 |
| 列表捲動 | RecyclerView 滑到底**被動**批次抓 4 頁（約 80 條），無 prefetch | `N7/P.java:296-310` |

穩定性四來源：**① 合約縮小**（自繪 App，不承諾終端體驗，畫面解析只需「抽資料」不需「還原體驗」）；**② 無狀態冪等交易**（每次從歸位開始，抓完即棄，不存在污染累積）；**③ Ctrl+L 全幅重繪**（把「增量重繪分類」整類問題買斷，代價是每指令多一輪流量——已被本專案 v5 採用，pttbbs 讀碼佐證見 protocol §2/§6）；**④ 失敗顯性化**（轉圈／錯誤對話框，而非錯亂畫面）。

誠實註記：BePTT 每個功能都是一條寫死腳本，PTT 介面一改就斷；它能這樣做是因為使用者**從未見過終端畫面**。穩定性的本質來源不是技術巧，而是**它承諾得少**。

反編譯 recipe：xapk(zip)→apk→portable Temurin JRE21 + jadx 1.5.1（置 `3rd_script/tools/`，gitignored），`jadx --no-res --no-debug-info -j 6 -d <out> <apk>`。踩坑：① jadx 留 `/* compiled from: Xxx.java */` 可還原混淆類名；② **大方法反編譯失敗會被整個略過**（樓層邏輯所在方法曾因此被誤判「不存在」）→ 補 `--single-class … --show-bad-code`（bad-code 條件式可能顛倒，以結構/字串為準）；③ dex 內 Big5 字串 MUTF-8 解碼會損壞，UTF-16 中文常數正常。

## 4. 若要走 D（App 式）：設計要點

**這不是走回頭路**：v1–v4.0 失敗的不是「長列表顯示」而是**混合模型**（DOM 無限捲動＋終端游標語意＋與 server 連續同步），所有接縫都長在「一半終端一半網頁」上。D 是換掉整個合約：資料層（文章條目陣列）與呈現層（虛擬列表）之間**沒有終端概念**，server 互動退化成三種無狀態交易（抓一頁、開一篇、刷新）；捲動＝純本地資料滑動，只觸發「補資料」不觸發「同步」。

- **桌面大視口卡頓疑慮成立但可解**：視口約 40–60 條、PTT 每頁 20 條，BePTT 式被動載入（滑到底才抓）約每滑 1.5 視口撞牆一次。緩解手段皆已有實證資產：主動水位預讀（維持前方 ≥3 視口，`easyReadingListPrefetchCount=200` 已 live 驗證 server 承受度）、骨架列、buffer 保留已抓區段、數字跳號 O(1) 隨機定位。
- **可直接重用**：`CommandQueue`（序列化＋timeout）、錨定 jump＋鏈式翻頁預讀、`parseListArticleNum` 系列、settle 內容謂詞法、黑名單過濾（降維成資料層 filter）、cassette 離線測試法＋錄製器。
- **整批拋棄**：read.c 視窗數學 parity（`list_window.js`）、`●` relabel 與污染防護、frozen／native 鏡像切換、pinned 門控（改在資料層處理）。這批恰好覆蓋最痛的那幾條不變量。
- **開放設計題**：快照過期（新文進板／刪文造成序號位移 → 開文交易前重跳序號＋標題指紋比對，mismatch 就地重抓）；進階操作（`[ ] =`、`/`、`Z`、發文）第一版一律不做，提供「切回原生模式」逃生門；雙模式切換 UX。
- **里程碑建議**：M1 唯讀列表視圖（虛擬列表＋骨架列＋水位預讀，cassette 離線測試先行）→ M2 開文／返回交易（含標題指紋重驗證）→ M3 黑名單／刪文過濾＋雙模式切換＋live soak。每階段獨立可驗收，中途砍掉不傷原生模式。
