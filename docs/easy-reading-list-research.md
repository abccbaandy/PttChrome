# 文章列表好讀模式：困難點本質與方向評估（研究報告）

撰於 2026-07-05，v4＋6 輪修復（`1277ddd`）之後。回答四個問題：困難點在哪／後續怎麼走／只為隱藏黑名單有無更穩方案／BePTT 式 App 顯示是否更穩。

## 0. TL;DR

| 問題 | 一句話結論 |
|---|---|
| 困難點本質 | 原生模式是「顯示玻璃」（server 單一真相源），好讀列表是在 80×24 字元鑰匙孔後維護**第二真相源**並與無規格的 server 持續對帳——成本曲線是結構性的，不是「還沒修完」 |
| 後續建議 | v4 **凍結**為 opt-in 實驗功能、停止追 parity 邊角；先做零風險的黑名單佔位美化；若還要投資，轉 App 式視圖而非繼續修 |
| 只為黑名單 | 更穩方案**已經在服役**：原生模式的就地遮蔽（`visibility:hidden`，零協定互動）。缺的只是把空白列變好看（佔位美化，小時級工作量） |
| BePTT 式重設計 | 結構上確實更穩（合約縮小＋無狀態冪等交易），且與已廢棄的 v1–v4.0 長列表**不是同一條路**；桌面滑動卡頓是預讀水位工程問題，用現成的鏈式預讀資產可解，非本質障礙 |

核心決策點（第 7 節）：好讀列表的產品價值到底是「隱藏黑名單」還是「更舒服地讀列表」——前者佔位美化即達標，後者才值得 App 式投資。

## 2. 困難點本質：為什麼比原生難一個量級

### 核心不對稱

原生模式的 client 是**顯示玻璃**：`term_buf` 只做 ANSI 解碼與畫格子，不理解畫面內容。游標、翻頁、選取、置底、搜尋——全部語意都在 server；server 怎麼畫，畫面就怎麼對，**任何 server 行為自動正確**。

好讀列表要在使用者與 server 之間插入一層自己的列表狀態（緩衝多頁、隱藏部分列、本地游標），從此 client 必須：**理解**畫面（分類指紋）、**預測** server（read.c 語意移植）、**對帳**（settle／expect）。單一真相源變雙真相源，任何同步誤差＝一個 bug。

### 六個結構性因素

1. **協定無規格**。唯一介面是 80×24 字元流；何時「回應結束」、哪幾列會髒、游標停哪，pttbbs 沒有合約，只能逆向原始碼＋錄影帶實錄（`docs/pttbbs-screen-protocol.md`）。每一條沒逆向到的行為＝上線後一輪修復（例：數字跳號完成時底列留空，早期 expect 等底列文字永遠等不到，`d6feebc` 補實錄不變量）。
2. **settle 判定**。server 寫入是增量、可黏包（OBUFSIZE 3072 拆包＋WS proxy 邊界 unknown），「畫面到齊」只能靠 50ms 靜默窗推定；而本地導覽約 30ms 一幀重繪與之交錯，gating 沒切乾淨就 settle 餓死（不變量 2b；症狀「按住 PgUp 無效」，`db0ae41`）。
3. **typeahead 跳繪**。pttbbs 在輸入 buffer 非空時直接跳過重繪（`mbbsd/screen.c:310`）——兩鍵並行在途，中間畫面就被吞。所以機器送鍵必須全序列化（CommandQueue 單 in-flight），連 `[` `]` `=` 都要拆成 jump→key 配對交易（不變量 12）。這正是 v3 的 source 級死因。
4. **隱藏列改變幾何**。隱藏 N 列後，24 行視窗要用其他頁的列補滿 → 必須超前抓頁（預讀鏈）＋自己算視窗（read.c 的 top/cursor 數學整套移植），還要在 server 真游標與本地假游標間往返對位（restore／resume／`●` relabel——`●` 污染列 bug 一族全部源於此）。
5. **狀態爆炸**。原生單態 vs「5 狀態 × 3 渲染模式 × 佇列 in-flight × 預讀鏈態」。轉移表要全枚舉測試；每個交互組合（例：menu 出口 × in-flight jump 重繪交錯）都是一個可能漏掉的格子。
6. **驗收標準無界**。核心原則要求「無黑名單時兩模式無可感知差異」——這把 QA 面拉大到 **PTT 的全部互動面**：`/` 搜尋、`Z`、精華區、水球、動態看板、推文數即時變化、刪文位移、短序號搜尋結果、置底文……native 對這一切「免費正確」，仿真層每一項都要分類、要嘛支援要嘛降級，漏一項就是一個症狀。

### 定性結論

v3→v4 已經換掉了最大病灶（timing heuristic → 內容判定＋序列化），剩下的 11+ 個症狀全部來自 ④⑤⑥——而這三項**不會因為修復而縮小**：每支援一個新互動面就再生一批邊角，每輪修復新增一條不變量，不變量之間再交互。這是結構性成本曲線，不是收斂中的掃尾。

## 3. 若只為隱藏黑名單：方案階梯

關鍵事實：**原生模式的就地遮蔽已經在服役**。`src/components/Screen.js:104-124`（PAGE_LIST 分支：作者黑名單＋標題黑名單＋刪除文無條件隱藏）→ `src/components/Row/index.js:36` 以 `visibility:hidden` 整列蓋掉。24 行格線不動、零協定互動、不可能有同步 bug。

| 方案 | 做法 | 協定介入 | 失敗模式 | 體驗 | 成本 |
|---|---|---|---|---|---|
| **A 現況遮蔽**（已服役） | 註記→`visibility:hidden` | 零 | 無 | 內容看不到，但留空白列；游標行經該列時整列（含游標字元）不可見；個別標記位移列 fall through 不隱藏（記載為可接受 under-hide，`docs/enhanced-addon.md:14`） | 已完成 |
| **A+ 佔位美化** | 隱藏列改渲染單行低調佔位（如「▁ 已隱藏：黑名單／已刪除 ▁」），游標在隱藏列時仍畫游標記號 | 零（純渲染層，重用 computeAnnotations→Row 現有管線） | 無 | 空白缺口變成有意義的摺疊條，游標不再消失 | **小時級** |
| **B 游標自動跳過** | 游標落隱藏列時自動補送同方向鍵 | 輕（送鍵） | 連續隱藏列連鎖、頁界觸發翻頁、與手速競態 | 游標不再停在屍體列 | 天級，中風險，可選 |
| **C v4 重排**（現行） | 雙真相源仿真 | 重 | 見第 2 節 | 缺口完全消失＋本地零延遲 | 已投 2 週＋，續修無界 |
| **D App 式視圖** | 見第 5、6 節 | 中（無狀態交易） | 載入等待顯性化（轉圈／骨架列） | 非 native 體驗 | 週級 |

結論：初衷「不想看到黑名單的文」在 A 就已達成；A+ 把「留白難看」也解掉，**零協定風險、幾小時工作量**。C 與 D 解的其實是另一個更高的目標——「像那些文不存在一樣連續閱讀」。要不要為那個目標付錢，是第 7 節的決策點。

## 4. BePTT 怎麼做到穩：反編譯要點

素材：`3rd_script/BePTT/`（v7.0.9 xapk 解包＋jadx 反編譯；**gitignored，本機研究素材，不隨 repo 散布**）。

### 機制

| 面向 | 實作 | 證據 |
|---|---|---|
| 連線 | SSH／Telnet／WebSocket 三模式使用者可切（`wss://ws.ptt.cc/bbs`），失敗時提示換線路 | `Z7/f.java`（連線主體）、ConnectPttActivity |
| 終端模型 | 72×80 `char[][]`＋色彩陣列，ANSI 用單一 regex 解析（`\e\[([0-9;]*)([ABCDHJKmsu])`） | `Z7/f.java:489,495` |
| 互動 | **寫死字串腳本**，每步「連按離開鍵盲退歸位 → 重新導航」，如 `"eeeqqqs"＋板名＋"\r\n$$…\f"`；甚至連按 10 個 `\x1b[D`（左鍵）盲退 | `jadx_out/sources/N7/P.java:301,305,580,800,1076` |

### 穩定性從哪來（四個來源）

1. **合約縮小**：UI 是自繪 App，不承諾任何終端體驗。畫面解析只需服務「抽出資料」，不需「還原體驗」——我們 v4 的 16 條不變量多數屬於後者。
2. **無狀態冪等交易**：每次操作從歸位開始，抓完即棄；不維護跨命令連續狀態，錯了重抓，**不存在污染累積**（對照 v4 的 `●` relabel 污染、快取 footer、鏈失效點清單）。
3. **Ctrl+L 全幅重繪**：把「增量重繪分類」這整類問題直接買斷——回應恆為全幅畫面，特徵字串一比對就知道到了沒。代價只是每指令多一輪重繪流量。此技巧有 pttbbs 讀碼佐證：`Ctrl-L` 是 igetch 全域熱鍵 → `redrawwin()+refresh()` 強制全屏重繪（`mbbsd/io.c:530-532`，見 `docs/pttbbs-screen-protocol.md` §2）。
4. **失敗顯性化**：畫面不符預期＝轉圈重試／錯誤對話框，使用者看到的是 loading，不是錯亂的畫面。v4 的誤判則直接呈現為體驗異常（閃現、裸露、卡 functionMode）。

誠實註記：BePTT 的代價在它自己身上也看得到——每個功能（信箱、發文、推文）都是一條寫死腳本，PTT 介面一改就斷；它能這樣做，是因為它的使用者**從未見過終端畫面**，沒有「跟原生比對」的期待。穩定性的本質來源不是技術巧，而是**它承諾得少**。

## 5. App 式重設計評估

### 先回答「這不就是走回頭路？」——不是

v1–v4.0 的長列表已經失敗兩次（v3、v4 上午版 `041f8c2`→`3971591` 日內廢棄），但失敗的不是「長列表顯示」，而是**混合模型**：DOM 無限捲動＋終端游標語意＋與 server 連續同步（綠色高亮條＝游標、prepend 要捲動補償、鍵盤仍是終端鍵）。所有接縫——捲動錨定黏著、延遲、綠條與 server 游標漂移——全部長在「一半終端一半網頁」的縫上。

BePTT 式是換掉整個合約：資料層（文章條目陣列）與呈現層（虛擬列表）之間**沒有終端概念**；server 互動退化成三種無狀態交易（抓一頁、開一篇、刷新）。捲動＝純本地資料滑動，永不觸發「同步」，只觸發「補資料」。失敗模式從「畫面錯亂」變成「骨架列多轉一下」。

### 與 v4 逐點對照

| 面向 | v4（原生視窗仿真） | App 式（BePTT 合約） |
|---|---|---|
| 體驗合約 | 與原生無可感知差異（無界 QA 面） | 自繪列表 UI，明示非終端 |
| 狀態 | 連續雙真相源對帳 | 每交易無狀態、冪等 |
| 回應判定 | settle 靜默窗＋內容謂詞（需處理增量重繪） | 可加 Ctrl+L 強制全幅＋特徵字串（更簡單） |
| 鍵盤 | 全鍵攔截／轉譯／passthrough 三分類 | 點擊＋捲動；進階操作交給原生模式 |
| 失敗表現 | 閃現／裸露／卡模式 | 顯性 loading／重試 |
| 資料時效 | 累積 buffer（可過期） | 快照＋重進重抓／下拉刷新 |

### 桌面大視口的卡頓疑慮（使用者問題四）——成立，但可解

量化：桌面視口約 40–60 條（估），PTT 每頁 20 條，每頁交易實測量級 100–400ms（v4 的 `adaptiveTimeoutMs`＝4×RTT clamp 800–3000ms 即為實測依據）。**BePTT 的被動式載入（滑到底才抓 4 頁）照搬到桌面，約每滑 1.5 個視口就撞牆一次——疑慮完全成立。**

但緩解手段全部已有實證資產：

1. **主動水位預讀**：維持視口前方 ≥3 視口（150–200 條）buffer。v4 預設 `easyReadingListPrefetchCount=200` 已在 live 驗證 server 承受度；鏈式翻頁（跳號錨定＋PgDn 連發＋RTT 自適應 timeout）已上線（不變量 5c）。
2. **骨架列**：預讀趕不上時渲染佔位列，資料到補繪——失敗顯性化，不會畫面錯亂。
3. **回捲零成本**：buffer 保留已抓區段（v4 的 evict 策略反向沿用、cap 放大即可）。
4. **隨機定位**：拉捲軸到任意位置／End 直接數字跳號 O(1) 定位、再向兩側補頁——PTT 的數字跳號給了 BePTT 逐頁走訪沒有的隨機存取能力。

結論：卡頓感是**預讀水位工程**，不是結構性障礙。真正要付的代價在體驗合約：這不再是終端。

### 資產盤點（v4 不是白做的）

| 去向 | 內容 |
|---|---|
| **直接重用** | `CommandQueue`（序列化＋timeout）；錨定 jump＋鏈式翻頁預讀；`parseListArticleNum` 系列（序號／置底／刪除文解析）；settle 內容謂詞法；黑名單過濾（`visibleListIndices` 邏輯降維成資料層 filter）；cassette 離線測試法＋錄製器 |
| **整批拋棄** | read.c 視窗數學 parity（`list_window.js`）；`●` relabel 與污染防護；frozen／native 鏡像切換；`[` `]` `=` 配對交易；restore 逐行還原；pinned 門控（App 式在資料層處理置底） |
| **可新增** | Ctrl+L 技巧簡化到齊判定（BePTT 實證） |

拋棄清單恰好覆蓋了 16 條不變量裡最痛的那一批（5、5b、5c、12、13、restore／resume 族）——因為它們全是 parity 呈現層的疤。

### 開放設計題（做 PoC 前要想清楚）

- **快照過期**：新文進板／刪文造成序號位移。候選解：開文交易前重跳序號＋標題指紋比對，mismatch 就地重抓一頁再開；列表頂放下拉刷新。
- **進階操作**（`[` `]` `=`、`/` 搜尋、`Z`、發文）：第一版一律不做，提供「切回原生模式」逃生門——v4 的 functionMode 自癒哲學升級到 UI 層。
- **雙模式切換 UX**：App 列表 ⇄ 原生終端的進出點與狀態交接。

## 6. 建議路線

1. **立即（無論後續走哪條路）**：做 A+ 黑名單佔位美化（第 3 節）。小時級、零風險、直接改善初衷場景。
2. **v4 處置：凍結**。保留為 opt-in 實驗功能（預設 off 不變）；只修「會影響原生模式」的回歸，**不再追 parity 邊角**。理由：現在測試全綠＋自癒降級在手，凍結成本低；續修的邊際收益結構性遞減（第 2 節 ④⑤⑥ 不收斂），同樣的工時投到下面第 3 點價值更高。
3. **續投資與否的決策點**（使用者決定）：
   - 好讀列表的價值＝**隱藏黑名單** → A+ 之後到此為止；v4 留作實驗品，日後可整批移除（拋棄清單見第 5 節）。
   - 價值＝**更舒服地讀列表**（無缺口、大視野、順滑） → 做 App 式 PoC，**明確放棄 native parity 合約**。里程碑：
     - M1 唯讀列表視圖：虛擬列表＋骨架列＋水位預讀（重用 CommandQueue／鏈式預讀／序號解析），cassette 離線測試先行；
     - M2 開文／返回交易（含標題指紋重驗證）；
     - M3 黑名單／刪文過濾＋雙模式切換＋live soak。
     每階段獨立可驗收，中途砍掉不傷原生模式。
4. **不建議**：在 parity 方向繼續修／補／優化。兩代「測試綠仍實測不穩」已經證明失敗面積在素材之外；每輪修復的產出是又一條不變量，而不變量清單本身就是維護負債。
